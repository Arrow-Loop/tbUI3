# Diagnostic files

> **HARD REQUIREMENT (owner, 2026-11-25).** Every log and diagnostic written by anything in this repository, now or in future, must (1) be stored only under `%LOCALAPPDATA%\tbUI3\Diagnostics\` through the shared `DiagnosticPaths.twin` helper, with no TEMP, project-folder, EXE-folder or other fallback, and (2) honor the single tbUI3 IDE Options toggle "Store logs and diagnostics": when it is off, nothing is written. Per-component flags may only refine detail beneath that switch. This binds every person and AI agent (Claude, Quill/ChatGPT, Codex and others). Do not remove logging between versions; the switch controls it. Full rule: [AGENTS.md](../AGENTS.md#logging-and-diagnostics-hard-requirement-owner-2026-11-25). The switch is in IDE Options under **tbUI3** and is saved as `HKCU\Software\VB and VBA Program Settings\tbUI3\Diagnostics\StoreLogs` (missing means on). While it is off, `DiagnosticsFile`/`DiagnosticsRoot` return nothing and nothing in the table below is written, development tools keep no transcripts, and native self-tests refuse to run. Compiled apps outside the IDE use the fixed `CompiledAppsStoreLogs` value for now (see ROADMAP).

All active first-party runtime diagnostics and development-tool transcripts now use **`%LOCALAPPDATA%\tbUI3\Diagnostics\`**. Open that path in Explorer. The package, add-in and updater share the same private `DiagnosticPaths.twin` implementation. Diagnostic failures do not fall back to TEMP, an executable directory or the user's project directory.

Development-tool transcripts are written directly into Diagnostics with their existing timestamped names. The portable Node/jsdom cache and transient publication work remain in `%LOCALAPPDATA%\ArrowLoop\tbUI3\DevTools\`; existing historical logs there are not moved. Reset-TestState.bat retains its separate recovery backups and manifests; its archive-diagnostics option includes new development transcripts. Preview and reset launchers do not gain a new transcript in this change.

Local diagnostic logs at known project roots and designated Diagnostics directories are excluded from release-source checks. The unified developer tool automatically commits already tracked or explicitly staged repository diagnostics along with its normal source checkpoints, per owner approval. Newly collected raw diagnostics are not added to the public source repository. The unified tool mirrors two private Diagnostics repositories using the dedicated local Git checkout rooted at the Diagnostics folder. Select C (Configure Diagnostics Sync) once per PC and provide the two distinct owning GitHub usernames. The tool reuses named GitHub CLI credentials or prompts for browser login during setup only, restores the previous active CLI account, and stores only usernames and verified repository IDs in the local development cache outside Diagnostics. The two private repositories must use main; both identities, private status, write access and IDs are checked before network Git transfer. D (Sync Diagnostics), configured startup/exit and successful or failed development/reset operations checkpoint local logs, fetch both histories, merge and push without force, then verify the same remote commit on both. Independent initial histories are retained. A failed merge or partial push leaves local commits intact; the next sync retries. If no local checkout exists, the tool initializes one in the existing dedicated log folder without overwriting files. No private destination identifiers or credentials are embedded in public source, and the tool does not change Git credential configuration. Original failures remain visible. Reset archive preserves checkout metadata. Diagnostic-only merge conflicts retain the local copy while preserving both versions in Git history. Source/resource conflicts are not resolved automatically.

No tracing flag is automatically enabled by this path change. Existing project/TEMP log files remain untouched as historical evidence, but new active code stops writing there. Historical research probe snapshots under docs/research are retained unchanged; they are not active application diagnostics.

Updater transaction contexts, approvals, recovery journals, backups, settings, receipts, downloads and WebView2 profile data remain in their operational locations under `%LOCALAPPDATA%\tbUI3\Updater\`. They are not disposable diagnostic output and were not moved. The updater's elevated worker does not append to user-controlled log files.

Rebuild the updated binaries to adopt the new routes. Consumers with an old embedded tbUI3 control package must re-import the rebuilt package; the repository's tbUI3Test embedded copy is already synchronized. No user project is silently rewritten. Stable control/form IDs and the separate core-package numbering are preserved.

## Startup troubleshooting

A passing engine self-test does not establish that WebView2 or the add-in/wizard initializes. `updater-startup.log` now records form initialization, environment/profile configuration, Ready, resource-filter creation, NavigateToString submission, fixed script resource requests and the final `updater:ready` handshake. Failures identify stage plus error number. The fallback page is written/verified atomically before the browser is opened; it displays the actual escaped error instead of claiming every failure means the Runtime is missing.

The earlier unqualified startup error is superseded by the accepted compiled startup run. The IDE argument path uses application `Command$` rather than the compiler host command line. If a new failure occurs, collect the current staged error and runtime version.

The 58/58 native report and successful compiled no-context startup are recorded in [native-startup-2026-11-23-passed.json](../tbIDE/Updater/validation/native-startup-2026-11-23-passed.json). The host authorizes only its exact generated UTF-8/Base64 document and about:blank, not arbitrary URLs. Embedded text conversion uses the package's whole-buffer UTF-8 conversion. Prior cumulative log entries and 42/54 and 57/57 reports are historical evidence; see CHANGELOG. IDE debug startup, integrated add-in launch and live update acceptance remain separate checks.

If startup fails, inspect `updater-startup.log` for the stage/error number, navigation decision, script requests and `updater:ready received`. Report current diagnostics through the user's approved private channel; do not publish private diagnostic sources, credentials, paths or raw logs in this repository. Raw logs can be synchronized by the unified tool only to the two configured and verified private Diagnostics repositories, explicitly via D or automatically at the configured workflow boundaries. Already tracked or explicitly staged repository diagnostic files can be synchronized by the unified development tool.
